# Real-World Basis Extrapolation Method

**Written 2026-08-16.** A reusable technique for deriving concrete **places, things, people, and settings** for
any location, at any scale, in any setting — from that location's
own real-world inspiration picks, via actual web research fused against what's already established in-fiction.
Directly requested by the developer while starting district Phase 6 (Thematic Breadth Catalog) work, but scoped
deliberately general: the same technique applies to any location, district or city, present or future.

**Relationship to the existing method:** this isn't a new invention from nothing — `City_Megasheet_Compilation_Guide.md`'s
Step 1.6 already does real-world research fused against in-fiction fact, for the Mega-Init's general identity pass.
This file names that same fusion technique explicitly and re-aims it at a narrower, more concrete target: not "what
does this place's overall character give the location," but **"what specific building, ritual, social role, tool,
or sub-space does this real place actually have — one this location could plausibly have its own version of."**

- **Cities:** `Worldspace/Locations-and-Levels/Outside-World/Tepenian-Federation/Locations/Cities/Inspirational-Influences.md` — one entry per city, Primary/Secondary/Supporting real-world picks.

Both already exist and are populated for every location — this method doesn't require generating new picks, only
using the ones already there more thoroughly than a single Mega-Init pass typically has room to.

## The process

**Step A — Pull the full pick list.** Every Primary/Secondary/Supporting entry for the location, not just the
Primary picks — Secondary and Supporting tier picks are exactly the ones the History Enhancement Template's own
validated finding already flagged as "tend to go uncited once a Primary pick anchors the district," which makes
them the most likely to still hold unused, concrete material.

**⚠ Do not stop at the first search result — extend research to wherever the topic naturally leads.** *(Added
2026-08-31, developer instruction.)* One search returning one usable fact is not the same as
the topic being exhausted. After every search, ask explicitly: **did this source name, cite, or gesture at
something else worth chasing** — a related institution, a named period, a person, a mechanism mentioned in
passing — **and did I chase it, or did I stop because I already had enough to write something plausible?**
"Enough to write something plausible" is exactly the threshold LAW 0 warns against accepting. Log open threads
that were noticed but not chased in the research log's own open-threads field (Step F below) — an unchased
thread is not a failure, but a *silently* unchased one is indistinguishable from one that was never noticed at
all, which defeats the whole point of logging.

**Step B — Research each pick as a real, specific place, not a category.** Run an actual web search on the named
real place itself (not "what are healing sanctuaries like" but "Epidaurus" specifically) — its actual documented
buildings, rituals, named roles, tools, and sub-spaces. The goal at this step is inventory, not interpretation:
what concrete, nameable things does this real place actually contain? A real-world site described only at the
category level ("an ancient Greek healing sanctuary") gives back nothing more specific than what's already
implicit in the pick; the same site researched properly gives back an abaton, a tholos, a specific ritual of
incubation-sleep for healing dreams — nameable, concrete, usable.

**Step C — Ask the fusion question per concrete detail found, not per pick.** For every specific building/
ritual/role/tool/sub-space Step B surfaced, ask: *does this location's own already-established character
plausibly produce its own version of this specific thing* — and if so, what would that version's name and
function actually be? This is the same fusion discipline the Compilation Guide's Step 1.6 already uses
("what does this specific real place's own documented character give back to the [location] that isn't already
there"), just applied at the level of individual concrete details instead of the location's overall identity.

**Step D — Cross-check against everything already established before writing anything down.** Per the
Compilation Guide's Step 2 discipline, every invented place/thing/person/setting needs to trace back to
something already canon — check the location's own Mega_Init, Full_Extrapolation, Deep Dive, Community
Infrastructure section (districts) or equivalent Local Culture sections (cities), and the location's Cross-
Reference Synthesis, before proposing something that might already exist under a different name or genuinely
contradict established fact.

**Step E — Write the result into the right target, following that target's own conventions.** For district
Phase 6 (Thematic Breadth Catalog) entries specifically: **people-derived entries stay role/archetype
placeholders, never invented proper names**, per the binding rule already in `District_Culture_Development_Plan.md`.
Places and things get named specifically, per the Compilation Guide's own "naming forces specificity" principle.

**⭐ Step F — Log the research in that location's own dedicated research log. Not optional.**
*(Standing developer instruction, 2026-08-30.)*

> **"When doing web research for building and developing locations, have a separate, distinct, dedicated file
> for each particular location that keeps a record of exactly what it was that was researched in order to find
> some-such-and-such-whatever particular piece(s) of information. That way, any time it ever becomes necessary,
> future iterations can refer back to things and possibly do further, deeper investigative research, if such a
> thing turns out to be necessary."**

**One file per location, `[Location]_Research_Log.md`, appended to and never rewritten.** For the 35 outer
cities: `Cities/Research_Logs/` — **see that folder's `README.md` for the full convention.** Districts, subnets,
structures and any other location type get one too, stored with their own material.

**Record, per session:** the date and which pass it served · **the deficit or question being researched
against** · **⭐ the exact search strings, verbatim** · the sources actually used, with links · a fact-by-fact
table of *what came back → which finding it became* · what was **withheld** (and what for) versus **omitted**
(and why) · **divergences from source** · and **⭐ open threads: sources surfaced but unread, questions not
chased, and what each might yield.**

**Why this earns its place rather than being bookkeeping.** A finished pass shows conclusions and hides
evidence, so the next session cannot re-check a claim, cannot tell a researched fact from an assumed one,
re-runs searches that have already been run, and — worst — **loses every thread that was deliberately left
hanging, which is usually the richest material available.** The log is the provenance layer.

**And it stays admissible.** A research log records *attributes*, never conclusions, so under `05` §6.1 it
remains a legitimate input **even to a later cold run on the same location** — unlike the pass it fed.

---

## Standing rule carried over: never evaluate picks by national/demographic matching

The Compilation Guide's own sharpened standing rule (2026-07-07) — a real-world pick's fit is judged purely on
structural/thematic fusion, never on whether it happens to share a founding nation or demographic with the
location with a founding population — applies here unchanged. Some sub-location types have no founding nation at all (a district of one city, for instance
isn't nation-founded the way outer cities are), so the literal collision this rule was written for doesn't arise
for district picks — but the underlying principle still generalizes: judge every fused detail on whether it
actually fits the location's own established character, never on any demographic or origin-matching basis.

## Worked example

> ⛔ **ARCHIVED** — `Universal_Location_Methodology/Test_Runs/Worked_Examples_Archive/` *(LAYERING LAW,
> `00_RUNBOOK.md`)*. **A full eight-pick run exists, showing what each tier actually surfaced and what it
> became.** **The method above stands without it.**

**What that instance demonstrated, stated generally — this is the transferable part:**

1. ***"Applying the method from memory" is not applying it.*** **The failing version recalled what it already
   knew about each pick, produced two thin generic items, and left half the picks completely untouched.**
   **Actual searching produced a concrete, unguessable detail from nearly every one.**
2. ⭐ **The unused lower tiers carried the best material.** **Picks previously dismissed as secondary or
   supporting produced the strongest results** — because **top-tier picks get absorbed into a location's
   identity summary early and spent, while lower tiers sit unexamined and still hold unspent specificity.**
3. **A real detail beats an invented one every time.** ***Nothing invented matched the sharpest researched
   particular.***
