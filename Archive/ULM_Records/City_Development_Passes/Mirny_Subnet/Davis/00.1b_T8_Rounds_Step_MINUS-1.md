### 1.3 ⭐⭐ `M-222` — READER A WAS SENT BACK, AND ITS POST-MORTEM FOUND THE REAL DEFECT

A was asked to **re-derive** both counts at byte level. ⛔ **It was deliberately not told the answers** — a count
copied from the orchestrator verifies nothing, and if A's premise had been true, the harness would have been
what was wrong. A returned:

```
$ tail -c 1 05_The_Input_Contract.md | xxd       ->  0a
$ tail -c 1 S01_Step_MINUS-1_....md  | xxd       ->  0a
   both: endswith(b'\n') = True,  count(b'\n') = len(splitlines())  -> 811 and 83
```

**Both figures were wrong, both by exactly +1, and A stated so plainly.** But the diagnosis is the valuable
part, and it is **an instrument defect, not a reader defect** *(A's own words)*:

> *"`LMID` index is `(811+1)//2 = 406` and `(83+1)//2 = 42` — **the same indices my inflated N produced,
> because integer division absorbs the off-by-one.** `LLAST` came from `tail -n 1`, which reads the file rather
> than a count. **That is precisely why the error survived**: every field that could have contradicted it was
> computed by a route that did not consult it, so the wrong number was load-bearing on nothing and was never
> challenged."*

⛔ **`LINES` floats free of every other field in the `PROOF` block.** `(N+1)//2` is insensitive to ±1 whenever
`N` is odd — **half of all files** — and `LLAST` is read from disk rather than derived from `N`. So the one
field the format cannot self-check is the one four readers got wrong.

⚠ **And no midpoint formula fixes it.** Checked: `N//2` catches `811→812` but collides on `810→811`. **Any
function that halves `N` collides on some `N`/`N+1` pair.** Changing the formula moves the blind spot; it does
not remove it.

**A's account of the mechanism, which is the transferable part:**

> *"`wc -l` returned 811 and 83. I believed the file had 812 and 84 lines. I reconciled the two by reaching for
> the one rule that makes `wc -l` under-report by exactly one — a missing trailing newline — and asserted it as
> observed fact in both PROOF blocks. **I never ran `tail -c 1`.** The premise was not a misreading of
> evidence; **there was no evidence. It was an explanation invented to dissolve a discrepancy**, and it is the
> same explanation three prior readers reached for, which is what makes it attractive: it is the locally
> correct answer to 'when does `wc -l` undercount,' and it requires no work to state."*

Root cause A identified in itself: **it took the count from a tool display's line numbering, then treated
`wc -l` as the thing needing reconciliation instead of as the ground truth it already was.**

> ⭐⭐ **THE RULE — and it is about a class of error, not about counting.** ***A reader can state a checkable
> byte-level fact about a file it genuinely read to the end, without checking it, inside a report whose entire
> purpose is verified reading.*** **The quoted fields were all honest. The number beside them was not, and the
> sentence justifying the number was invented.** **Verifying that a reader READ something does not verify the
> claims it makes ABOUT what it read** — and `T8` was built on the assumption that it does.

### 1.4 THE FIX — implemented and controlled, not just recorded

`triple_read_verify.py` now checks **the fabricated premise directly**, independently of whether the arithmetic
survives: if a `PROOF` block asserts *"no trailing newline"* (or any variant) about a file that **does** end in
`0x0a`, the block **FAILS** — even when its `LINES` figure is correct.

**Control suite, raw:**

```
  POSITIVE (expect UNANIMOUS)        -> UNANIMOUS - CLEARED TO WRITE
  NEG-1 quote out of range           -> ⛔ NOT UNANIMOUS - DO NOT WRITE.
  NEG-2 llast out of range           -> ⛔ NOT UNANIMOUS - DO NOT WRITE.
  NEG-3 LRANGE=FULL on ranged file   -> ⛔ NOT UNANIMOUS - DO NOT WRITE.
  NEG-4 outright fabrication         -> ⛔ NOT UNANIMOUS - DO NOT WRITE.
  NEG-5 fabricated newline premise   -> ⛔ NOT UNANIMOUS - DO NOT WRITE.
  REAL ROUND 2 (all three readers)   -> UNANIMOUS - CLEARED TO WRITE
```

⭐ **`NEG-5` is the new one and the point of the exercise: its `LINES` value is CORRECT (811) and it fails
anyway,** because the sentence beside the number is an unverified byte-level assertion. **A right answer must
not launder a fabricated premise** — the premise is what will be wrong next time, on a file where the
arithmetic does not happen to survive.

**Also carried into the `PROOF` spec** *(A's own recommendation, adopted)*: `LINES` must be derived by
`awk 'END{print NR}'` or `splitlines()`, **never from a tool display's line numbering**, and the words *"no
trailing newline"* must never appear in a `PROOF` block unless `tail -c 1 | xxd` is shown beside them.
